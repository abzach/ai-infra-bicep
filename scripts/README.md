# PowerShell automation

| Script | Purpose |
|---|---|
| `../main.ps1` | Root dispatcher for `dev|uat-connect`, `dev|uat-deploy`, and `dev|uat-clean` commands |
| `deploy.ps1` | Validate context, self-remediate missing role-assignment permission, apply component deployment flags, skip already-current environments, preview/deploy Bicep, publish runbooks through ARM, configure diagnostics, sync secrets through ARM, bootstrap the VM, and hand off local credentials |
| `cleanup.ps1` | Preview or delete tag-validated environment resources while preserving Key Vault and the VM OS disk |
| `rdp.ps1` | Converge the jumpbox NSG to `allow-rdp-user`, temporary `allow-rdp-deployer`, and `deny-rdp-all` |
| `show.ps1` | Read `vm-admin-password` from private Key Vault inside the jumpbox via managed identity and print it only to the invoking console |
| `config.ps1` | Seed missing `variables/*.yaml` from their `.example`, then parse, merge, derive, and validate YAML configuration including deployment-flag dependencies |
| `common.ps1` | Shared output, retry, and resource helpers |
| `setup.ps1` | Install and configure the chat application inside the VM |
| `test.ps1` | Static, deployed-resource, smoke, and dual-model tests; deployed-resource validation verifies either the configured image and Azure Disk Encryption extension, or the configured attached OS disk with retained encryption, and static builds use the platform temporary directory on Windows and Linux |
| `scan.ps1` | Validate generated template security invariants, including VM- and NSG-scoped Automation roles, Static Web Apps Free SKU, Cosmos DB free-tier/private-network guardrails, and API Management Consumption tier |
| `safety.ps1` | Scan markdown and instruction files for AI safety, prompt injections, jailbreaks, hidden unicode smuggling, and harmful instructions |

Use PowerShell 7+. `deploy.ps1` installs or upgrades the Azure CLI-managed Bicep binary to the latest available release without prompting before continuing. Top-level scripts under `automation/` are parsed, hashed, provisioned, uploaded, and published as Automation runbooks; schedule links are created only after publication, and what-if mode performs validation and preview only. Normal reruns exit early only when all expected resources, runbook schedule links, and schedule properties match the local desired state and the recorded `desiredStateHash` matches the local source/configuration inputs; use `-ForceRedeploy` to bypass this guard. Local successful deployments place a plaintext credential handoff under ignored `.local/credentials/`; move the password to a password manager, delete the file, and rotate the VM password. CI never prints or writes that credential.

Environment-scoped commands load `subscriptionId` from `variables/<env>.yaml`, set the Azure CLI context to that subscription, and derive the four-character resource-name suffix from it before issuing Azure reads or writes. This applies to deploy, connect/RDP, password display, cleanup, and deployed-environment test modes, so the scripts do not depend on whichever subscription was active before invocation.

## Local subscription-state cache (`.local/cache/subscription-state.json`)

`deploy.ps1` caches two slow, rarely-changing preflight results in a git-ignored `.local/cache/subscription-state.json` file so reruns against the same subscription skip them instead of repeating the same network round trips:

- **Resource provider registration** (`Register-RequiredResourceProviders` in `common.ps1`): once every required provider namespace is confirmed `Registered` for a subscription, that result is cached (keyed by subscription ID and a hash of the namespace list) for 7 days. A changed namespace list, a different subscription, or an expired entry always falls back to a live `az provider show` check.
- **Bicep CLI latest-version check** (`Update-BicepCli` in `common.ps1`): the `az bicep list-versions` network call is cached (keyed by the special `machine` entry, since it isn't subscription-scoped) for 24 hours. The cheap local `az bicep version` check and install/upgrade logic still always run.

The cache is best-effort: a missing, corrupt, or unwritable cache file is never fatal, and every cached check silently falls back to a live one. It stores only registration-state booleans, version strings, and UTC timestamps — never secrets, credentials, or tokens — and is never committed (see the root `.gitignore` `.local/` entry). Delete the file, or the whole `.local/cache/` directory, at any time to force a full recheck on the next run.

## Local troubleshooting logs (`.logs/`)

`deploy.ps1`, `cleanup.ps1`, and `test.ps1` dot-source `common.ps1`, which mirrors every `Write-Task`/`Write-Exists`/`Write-Needed`/`Write-Info` console message into a git-ignored `.logs/ai-infra.log` file at the repo root (see the root-level `.gitignore` `.logs/` entry). Only those already-curated messages are persisted — never raw Azure CLI/API output — so the file stays small and never contains secrets by construction; as defense-in-depth, `common.ps1` also redacts any password/secret/token/key/bearer-token/SAS-signature-shaped substring before writing a line. The log rolls over at 5 MB: the active file is renamed to `ai-infra.log.old` (overwriting any previous one) and a fresh `ai-infra.log` is started, so at most two files (current + old) ever exist. `.logs/` is local-only and must never be committed.

At script completion, `common.ps1` prints an execution timing summary table and writes the same table to `.logs/ai-infra.log` with `TIME` entries. The summary includes every `Write-Task` operation classified as a stage, step, or resource operation, plus a final total duration row, so deployment and cleanup performance can be tuned over time. Existing traps also emit the timing summary before failed scripts exit.

## `deploy.ps1` behavior worth knowing

- **Role-assignment preflight.** If the deploying identity has neither `Owner` nor `User Access Administrator` at subscription scope, the script attempts to grant itself `User Access Administrator`, then (interactive users only) attempts Entra `elevateAccess` and retries, re-verifies with backoff, and only then fails with the exact remediation to request. `-SkipRoleElevation` skips the elevation attempt; CI runs skip it automatically.
- **Component deployment flags.** `deployStorage`, `deployLogAnalytics`, `deployAiFoundry`, `deployVm`, `deployAutomation`, `deployPostgres`, `deployStaticWebApp`, `deployCosmosDb`, `deployApiManagement`, and `deployAppService` from the environment YAML are passed to Bicep and drive lifecycle handling. A `false` value removes that component and its component-specific private endpoints and DNS resources in dependency order before the incremental ARM deployment. `deployAiFoundry` creates the current `AIServices` account/project, private Search, Agent subnet, connections, RBAC, and capability host. During migration, the script validates those resources and model deployments before purging the legacy AML Project and Hub. Key Vault, base networking, Azure OpenAI, their private endpoints, and the shared managed identity remain protected.
- **Workload-to-foundation migration.** Foundry, the jumpbox VM and OS disk, Automation, API Management, and the App Service plan/app live in the foundation resource group. Before Bicep runs, the script moves eligible copies left in the workload group (Spot VMs are recreated on a detached and moved OS disk). A legacy Foundry account and its projects are deleted and purged, then recreated by Bicep because moving them breaks Agent Service. `-WhatIf` only previews these steps. See [Resource Groups](../docs/resource-groups.md#migrating-an-existing-environment).
- **Foundry private endpoint recovery.** When account recreation leaves its private endpoint `Disconnected`, the script removes that endpoint before ARM deployment; Bicep recreates it. Connected endpoints are retained. `agentRecoverySubnetAddressPrefix` can select an unused delegated subnet if the previous Agent Service subnet retains a service association link.
- **VM app bootstrap recovery.** A matching Key Vault content hash is not enough to skip VM bootstrap: the script also checks for the guest chat launcher through VM Run Command. A recreated VM missing that launcher receives the app package even when the source files have not changed.
- **Public IP DNS label.** `vmPublicIpDnsNameLabel` from the environment YAML is passed to Bicep for the VM public IP. Empty means no public DNS label; a value such as `az-swe-aifp` creates `<label>.<location>.cloudapp.azure.com`.
- **RDP allowlist.** Environment YAML addresses populate stable `allow-rdp-user`; the detected deployment/connection IP populates temporary `allow-rdp-deployer`; `deny-rdp-all` remains last. Use `../main.ps1 dev-connect` or `../main.ps1 uat-connect` to refresh access without deployment. The weekly Automation runbook removes only `allow-rdp-deployer`.
- **Connect password display.** Because Key Vault public access is disabled and ARM never returns secret values, `*-connect` first verifies that the VM is running and its agent is ready, then uses VM Run Command to read `vm-admin-password` from the private endpoint with the VM managed identity. VM provisioning, power, agent, and Run Command failures are reported before any password is handled. The VM returns the marked password payload to `show.ps1`, which decodes it and prints it only to the invoking console; the script does not use repository logging or persist the returned value.
- **Selective cleanup.** `*-clean` enumerates only tag-validated environment resource groups, deletes their resources in dependency order, and preserves the environment Key Vault and VM OS disk (including the disk named by `vmExistingOsDiskId`). Resource-group containers remain.
- **VM password preservation.** A rerun never changes a password the VM already has. A new password is generated only on first deploy, when the VM is being recreated (Spot/Regular priority change), or when `-RotateVmPassword` is passed. Otherwise the Key Vault sync and `az vm user update` are skipped, and the previously issued password remains valid.
- **Role-assignment preservation.** Template-managed role assignments use deterministic names and are left in place on normal redeployments. This avoids RBAC propagation gaps if a later deployment step fails.
- **Flag-aware live validation.** `Validate` and `Smoke` require enabled optional services (including PostgreSQL and App Service) to exist with their configured secure/free-tier settings and require disabled services to be absent.
